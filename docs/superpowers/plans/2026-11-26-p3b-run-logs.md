# P3b Run-Logs, Live-Urteil, MAIN-Welt-Fehler: Umsetzungsplan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In diesem Projekt: inline mit TDD (D-031, D-037, D-038), am Ende ein frischer Gesamt-Review.

**Goal:** Jeder echte Run wird nach D-005 protokolliert, als Datei exportiert, geprüft nach `runs/` übernommen und zusammengefasst. Das Live-Urteil erkennt typisierte Pausen und Stillstand je Bildschirm. Fehler aus der MAIN-Welt erscheinen im Bot-Log.

**Architecture:**
- Die Strategie liefert zu ihren Entscheidungen ein optionales `trace`.
- Ein reiner `RunRecorder` in `src/core/log/run-log.ts` wird vom `BotController` gefüttert und erzeugt Zeilen, Zusammenfassungen und das Export-Bündel.
- Das Overlay lädt das Bündel herunter. `scripts/runs-lib.mjs` scannt es und schreibt `runs/`.
- Der Live-Test urteilt mit einem reinen `ProgressTracker`.

**Tech Stack:** TypeScript, Vitest (happy-dom), Playwright, Node-ESM-Skripte.

**Reihenfolge der Ausführung:** T1, T3, T2, T4, T5, T6, T7, T8. T2 braucht `PauseKind` aus T3.

**Spec:** `docs/superpowers/specs/2026-11-26-p3b-run-logs-design.md` (D-038)

## Global Constraints
- Kein Lesen oder Schreiben von Spielschlüsseln im localStorage (`poke_*`, `pkrl_*`). Der Recorder bekommt nur `GameState` (R-145, R-148).
- Nichts nach `runs/`, ohne dass `scanSecrets` leer ist. Fehlermeldungen nennen Muster und Datei, nie den gefundenen Wert (R-148, R-210).
- Format-Kennung des Exports genau `pkbot-runs/1`. Dateiname `pkbot-runs-<YYYYMMDD-HHMMSS>.json`. Ablage `runs/<YYYY-MM-DD>-<HHMMSS>-<rand4>/` mit `decisions.jsonl` und `summary.json`.
- D-005-Zeilenfelder genau: `ts, run_id, step, game_version, screen, state, options, scores, chosen, reason, confidence, profile, mode, outcome`.
- Grenzen: `maxRuns = 10`, `maxLines = 3000` je Run, `errors` höchstens 50 je Run.
- Budgets im Live-Test: `battle-screen` 120 s, `map-screen` 180 s, sonst 90 s; gesamt 4 min (`STALL_MS`); Nachlauf höchstens 4 min.
- Pausen-Arten genau: `user | finished | config | unsupported | inconsistent | failing | internal | blocked | stalled`. Fehler sind `inconsistent, failing, internal, blocked, stalled`.
- Keine Verhaltensänderung der Strategie: Alle bestehenden Engine- und Strategy-Tests bleiben unverändert grün.
- Userscript-Bundle bleibt ES2020 und Safari 15 (`npm run build` prüft). `src/core` und `src/ui` importieren nie aus `src/platform/{chrome,userscript}` (R-032).
- Lint-Regeln aus D-036 gelten: kein stilles `catch`, keine schwebenden Promises.

## Review Focus
1. **Seite neu geladen, Bridge-Zähler beginnt wieder bei 0:** Der Reader muss `errSeq < lastSeq` als Neustart erkennen und wieder ab 0 holen, statt nie mehr Fehler zu melden. Test in Task 5.
2. **Pause, Fortsetzen, weiterspielen im selben Run:** Der Run darf nicht doppelt gezählt und nicht geschlossen werden. Erst `stop` schließt ihn. Test in Task 2.
3. **Export ohne einen einzigen Run** (frischer Start, sofort exportieren): ein gültiges Bündel mit `runs: []`, kein Fehler. Auch `writeRunDirs` schreibt dann nichts. Tests in Task 2 und Task 6.
4. **Ping-Pong zwischen zwei Bildschirmen ohne Fortschritt:** Das darf nicht als Fortschritt zählen, die Budgets müssen greifen. Test in Task 7.
5. **Ein Spielname oder Item-Name, der wie ein Spielschlüssel aussieht** (etwa `poke_ball` in einer Begründung): Er darf den Scan nicht auslösen, nur die sensiblen Schlüssel. Test in Task 6.
